# Convenciones del proyecto

Resumen de lo que explica `README.md`. Si algo de aquí y el código discrepan, manda el código. Antes de escribir código de Next, léase la guía correspondiente en `node_modules/next/dist/docs/`: esta versión (16) cambia APIs y convenciones respecto a las anteriores (`proxy.ts` en vez de `middleware.ts`, `params` asíncronos, tipos `PageProps`/`LayoutProps` generados).

- **Una app Next 16, una sola página, dos idiomas, sin CMS**: `app/[locale]/page.tsx` renderiza `app/[locale]/landing-page.tsx`, que compone las secciones según `config/site.config.ts`. No se añaden más páginas: cualquier contenido nuevo es una sección de la portada. El contenido vive en `messages/{es,en}.json` (todo lo que se lee) y en `constants/` (lo que no cambia con el idioma: enlaces, imágenes, orden de los proyectos).
- **Idiomas**: next-intl con `localePrefix: "as-needed"` (`/` español, `/en` inglés). Ningún componente escribe texto visible: siempre `useTranslations` (o `getTranslations` en funciones asíncronas). Las dos JSON llevan las mismas claves; el español es el catálogo que tipa `t()` (`types/next-intl.d.ts`), así que una clave nueva se añade en los dos archivos en el mismo commit. Las listas se leen con `t.raw` envuelto en `lib/message-list.ts`. Las anclas (`#proyectos`…) y los enlaces no se traducen. Los enlaces internos usan `Link` de `i18n/navigation.ts`, no el de `next/link`.
- **Archivos**: kebab-case con sufijos `.section.tsx`, `.comp.tsx`, `.hook.ts`, `.const.ts`, `.types.ts`; named exports (default sólo en archivos de App Router); sin barrels, imports `@/...`.
- **Componentes**: Server Components por defecto; `"use client"` sólo en la hoja que tiene el estado (hoy, el menú del teléfono). Imágenes con `next/image`, nunca `<img>`. `components/site/` es espejo de la página: `sections/shell/` (cabecera, pie), `sections/home/<sección>/` (una carpeta por sección con su `.section.tsx` y sus `.comp.tsx`) y `shared/` (piezas que reutilizan varias secciones). Sin carpetas `common`.
- **Idioma del código**: los comentarios van en inglés, como los identificadores; el copy que ve el usuario está en los mensajes, así que un comentario que cite un rótulo lo cita tal cual en español.
- **CSS**: BEM estricto (`bloque__elemento`, modificador `_clave_valor`), un archivo por componente y TODAS sus reglas anidadas bajo el selector raíz con nesting nativo (`&`), media queries dentro del bloque, desktop-first con un solo corte de teléfono (`max-width: 767px`). Tokens `--color-*`, `--font-*` y `--site-*` en `app/[locale]/globals.css`, que también tiene las clases compartidas (`section`, `section-title`, `eyebrow`, `button`, `skip-link`). Sin Tailwind ni CSS-in-JS. Las variantes de móvil que cambian de sitio un elemento se resuelven con `order` o `display: contents`, no duplicando marcado; cuando el diseño del teléfono es otro texto (firma corta del pie, «Disponible» en vez de «Disponible para vacantes») se renderizan los dos y el CSS muestra uno.
- **Datos y lógica**: lo que se puede probar sin React va a `lib/` (función pura + `*.test.ts` al lado). Los componentes no formatean ni recortan cadenas por su cuenta.
- **Deuda**: lo que se encuentra y no se arregla va a `IMPROVEMENTS.md` (área, prioridad y cómo abordarlo); las tareas mecánicas, a `todos.md`. Los dos están en inglés.
- **Documentación**: **todo cambio importante se documenta en el mismo commit**, no después: `README.md` si cambian puesta en marcha, scripts, contenido o rutas; `AGENTS.md` si el cambio ES una convención; `IMPROVEMENTS.md`/`todos.md` para la deuda encontrada o resuelta.
- **Antes de dar algo por terminado**: `npm run typecheck`, `npm run lint`, `npm test` y `npm run build` en verde. Rendimiento y layout, siempre contra `npm run build && npm run start`, nunca contra `next dev`; en móvil, con emulación real de 390 px (Chrome sin emular no baja de ~500 px de ancho y no dispara las media queries de teléfono).
